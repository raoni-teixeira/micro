O #pragma config mínimo para o PICSimLab, linha a linha

A ideia

Os bits de configuração não são registradores: são gravados na memória de programa junto com o código e decidem, antes da primeira instrução, de onde vem o relógio, se o watchdog está ligado e o que alguns pinos são. O programa não os muda em tempo de execução.

O valor de fábrica de vários deles não serve para o curso. Por isso o simulador precisa deste bloco no topo do main.c:

#include <xc.h>

#pragma config FOSC   = HS   // cristal, sem PLL
#pragma config WDT    = OFF  // watchdog desligado
#pragma config LVP    = OFF  // RB5 livre
#pragma config MCLRE  = ON   // pino 1 é o reset
#pragma config PBADEN = OFF  // RB0–RB4 digitais

#define _XTAL_FREQ 16000000UL // = relógio do PICSimLab

Linha a linha

BitValorO que fazSem a linha (valor de fábrica)
FOSCHSOscilador a cristal de alta velocidade (acima de 4 MHz), sem PLL. Com o CPUDIV de fábrica, a CPU roda na frequência do cristal: 16 MHz dão TCY = 4 / 16 MHz = 250 nsOutro modo de oscilador: o programa roda em outra frequência, ou não roda
WDTOFFDesliga o watchdog, o temporizador que reinicia o chip se o programa não o zerar a tempoLigado: com o divisor de fábrica (1:32768), o programa reinicia sozinho a cada ~2 min
LVPOFFDesliga a gravação em baixa tensãoLigada: RB5 vira o pino PGM e deixa de ser E/S comum
MCLREONO pino 1 é o MCLR: nível baixo reinicia o chip. É o botão de reset da placaJá é ON de fábrica; a linha deixa a escolha visível. Com OFF, o pino vira RE3, só entrada, e o botão de reset não reinicia
PBADENOFFRB0–RB4 começam como E/S digitalComeçam analógicos: o botão em RB0 lê sempre 0 até o programa mudar o ADCON1

PBADEN e ADCON1PBADEN define só o estado no reset. O ADCON1 escrito pelo programa vale depois dele, para qualquer valor de PBADEN: ADCON1 = 0x0F deixa todos os pinos digitais; 0x0E deixa só o AN0 analógico.

O relógio: _XTAL_FREQ

O #pragma diz de onde vem o relógio, mas não quanto ele vale. Quem decide a frequência é o cristal — no PICSimLab, o campo de relógio da janela principal. O _XTAL_FREQ só informa ao compilador esse valor, para que __delay_ms e __delay_us contem os ciclos certos.

Relógio no PICSimLab_XTAL_FREQResultado
16 MHz16000000ULAtrasos certos; TCY = 250 ns, como no kit
8 MHz16000000ULTodo atraso dura o dobro do pedido
16 MHz48000000ULTodo atraso dura o triplo do pedido

No simulador e no kit

No PICSimLab o chip começa do zero, e o #pragma config do programa é o que vale. No XM118 os bits de configuração foram gravados junto com o bootloader, que não os regrava: o #pragma config da aplicação é ignorado, e o kit roda a 16 MHz de CPU de qualquer jeito.

Para o mesmo main.c servir aos dois, o bloco fica dentro de uma condição — como no código de exemplo do curso:

#if defined(PLACA_PICSIMLAB)
#pragma config FOSC = HS, WDT = OFF, LVP = OFF
#pragma config MCLRE = ON, PBADEN = OFF
#endif

Por issono kit, um programa que esquece o ADCON1 pode funcionar com o botão em RB0 — o PBADEN do bootloader já resolveu — e falhar no simulador. A causa é a mesma linha de configuração, presente numa placa e ausente na outra.
